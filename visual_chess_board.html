Chess Move Validator - Visual Representation

Demonstrating Four-Layer Automata Theory Architecture

Current Game State

Current Turn: White

Layer 1: Piece-Specific DFAs

Each chess piece type has its own Deterministic Finite Automaton for movement validation.

Knight DFA States:
START → VALID_L_SHAPE → DESTINATION_REACHED
INVALID_L_SHAPE (rejecting)
INVALID_DESTINATION (rejecting)
Rook DFA States:
START → SAME_ROW/SAME_COL → PATH_CLEAR* → DESTINATION_REACHED
BLOCKED (rejecting)
INVALID_DIRECTION (rejecting)
INVALID_DESTINATION (rejecting)

Layer 2: History-Dependent FSM

Tracks historical information needed for castling and en passant.

Castling Rights Tracking:
White King: Has not moved | White Kingside Rook: Has not moved | White Queenside Rook: Has not moved
Black King: Has not moved | Black Kingside Rook: Has not moved | Black Queenside Rook: Has not moved
En Passant Target: None

Layer 3: Move Sequencing

Processes moves in order, validating each through Layers 1-4.

Validation Flow:
Move Input → Layer 1 (DFA) → Layer 2 (FSM) → Temp Move Application → Layer 4 (Safety) → Move Accepted/Rejected

Layer 4: Safety Filter

Uses OR logic to check if king would be in check after move.

Safety Check Logic:
King in check IF:
  ∃ opponent piece: can_attack(piece, king_square)
Move is safe IF: ¬(King in check)
