Layer 1: Deterministic Finite Automata (DFAs) for Piece Movement

Each chess piece type has its own DFA that validates whether a move follows the piece's movement rules. The DFA processes the move as a sequence of checks, transitioning through states based on board conditions.

Layer 2: History-Dependent Finite State Machine

Castling Rights FSM

State Tracking:

State Variable Initial Value Updated When Purpose
white.kingside true White king or h1 rook moves Can castle O-O?
white.queenside true White king or a1 rook moves Can castle O-O-O?
black.kingside true Black king or h8 rook moves Can castle O-O?
black.queenside true Black king or a8 rook moves Can castle O-O-O?
Why FSM?
Castling requires knowing if a piece has ever moved in the entire game history. A DFA has fixed memory (finite states), but tracking "has this ever happened?" requires unbounded memory - hence we need an FSM.
En Passant FSM

State Variables:

  • en_passant_target: Square where en passant capture is possible (or null)
  • last_move: The immediately previous move (for en passant validation)

FSM Transition Logic:

→

→
EN_PASSANT_AVAILABLE
EN_PASSANT_AVAILABLE
→ (after opponent move)
NO_EN_PASSANT
Window of Opportunity:
En passant is only available immediately after an opponent's two-square pawn advance. This requires remembering the exact previous move - another reason why DFAs are insufficient.
FSM vs DFA Comparison
DFA Memory: O(1) - Fixed number of states
FSM Memory: O(n) - Can grow with input length (move history)

Sequential Processing:
Each move validates against the current game state. Valid moves update the state, affecting validation of subsequent moves. Invalid moves terminate the sequence.

Simple Alternation:
White moves first, then players alternate turns. This is a simple 2-state FSM that tracks whose turn it is.
Game State Evolution

State Components Tracked:

  • Board Position: 8×grid with piece placement
  • Turn Indicator: white/black
  • Castling Rights: 4 boolean flags
  • En Passant Target: 1 square or null
  • Move History: Sequence of all moves
State Size:
• Board: 64 squares × 13 possibilities (empty + 6 white + 6 black pieces) = ~8.3 bits/square
• Additional tracking: ~16 bits
• Total game state: ~550 bits of information

This demonstrates how Layer 3 manages evolving state through the move sequence.

Layer 4: Safety Filter and Check Detection

Safety Filter Logic
Move is SAFE iff:
¬(∃ opponent piece p: CAN_ATTACK(p, our_king_after_move))
De Morgan's Law Application:
Instead of checking if ALL pieces are safe (AND), we check if ANY piece attacks (OR)
and negate the result. This is computationally more efficient.
Find Our King
→
Check All Opponent Pieces
→
OR-Combine Attacks
→
¬(Any Attacker) = SAFE
→
(Any Attacker) = UNSAFE
Check Detector Logic
Move gives CHECK iff:
∃ our piece p: CAN_ATTACK(p, opponent_king_after_move)
Symmetric Logic:
Safety Filter: ¬(opponent can attack us)
Check Detector: (we can attack opponent)
Both reuse the SAME Layer 1 movement logic!
Find Opponent King
→
Check All Our Pieces
→
OR-Combine Attacks
→
(Any Attacker) = CHECK (+)
→
¬(Any Attacker) = NO CHECK
Logic Reuse Demonstration

Shared Components:

  • RookDFA: Used for move validation AND attack detection
  • BishopDFA: Used for move validation AND attack detection
  • KnightDFA: Used for move validation AND attack detection
  • Etc. for all piece types
Architectural Benefit:
• No duplicated movement logic
• Consistent behavior between validation and attack detection
• Easy to modify - change in one place affects both uses
• Demonstrates separation of concerns and modular design
